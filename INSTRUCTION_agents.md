## Инструкции для агентов-исполнителей

---

### Общие правила

```
1. КАЖДЫЙ коммит должен проходить тесты. Никаких исключений.
2. КАЖДАЯ новая функция должна иметь тест. Без теста = не сделано.
3. КАЖДОЕ изменение архитектуры должно быть задокументировано.
4. КАЖДОЕ изменение конфига должно быть отражено в .env.example.
5. НИКОГДА не коммитить .env, секреты, ключи, пароли.
6. НИКОГДА не удалять работающий код без замены и тестов.
7. НИКОГДА не менять публичный API без миграции.
8. ПРИОРИТЕТ: безопасность > надёжность > функциональность > скорость.
```

### Правила коммитов

```
Формат сообщения коммита:
  <тип>(<область>): <краткое описание>

  [опциональное тело]

  [опциональный футер]

Типы:
  fix: исправление бага
  feat: новая функциональность
  refactor: рефакторинг без изменения поведения
  test: добавление/обновление тестов
  docs: документация
  chore: рутинные задачи
  security: исправления безопасности
  perf: улучшения производительности
  style: форматирование без изменения логики
  ci: изменения в CI/CD

Примеры:
  fix(execution): correct 24h TTL for M5 signals
  feat(mt5_adapter): add rate limiter and cache
  refactor(risk): unify risk logic into RiskEngine
  test(trade_group): add dust allocation tests
  docs(architecture): add module interaction diagrams
  security(api): add bearer token authentication
```

### Правила тестирования

```
1. Каждый новый тест должен быть в соответствующем файле:
   execution/tests/test_<module>.py
   features/tests/test_<module>.py
   model/tests/test_<module>.py
   и т.д.

2. Имя теста должно описывать что проверяется:
   test_allocate_small_volume_dust
   test_geometry_hash_includes_risk
   test_circuit_breaker_ignores_swaps

3. Тесты должны быть изолированы:
   - Использовать фикстуры для временных файлов
   - Не зависеть от внешних сервисов
   - Не зависеть от порядка выполнения

4. Тесты должны быть быстрыми:
   - Юнит-тесты < 1 сек
   - Интеграционные тесты < 10 сек
   - E2E тесты помечать @pytest.mark.e2e
```

---

### Правила безопасности

```
1. НИКОГДА не коммитить:
   - .env
   - *.key, *.pem
   - Пароли, токены, секреты в коде
   - Базы данных (*.sqlite)
   - Логи

2. Все секреты только через переменные окружения

3. Все эндпоинты API должны быть защищены

4. Все SQL-запросы параметризованы

5. Никакого shell=True в subprocess
```

---

### Правила документации

```
1. Каждый новый модуль должен иметь:
   - Docstring с описанием ответственности
   - Описание входов и выходов
   - Описание зависимостей
   - Пример использования

2. Каждое изменение поведения должно быть отражено в:
   - docs/ARCHITECTURE.md
   - docs/CHANGELOG.md
   - README.md (если нужно)

3. Каждая новая миграция должна быть описана в:
   - docs/MIGRATIONS.md
```

### Критерии завершения

Работа считается завершённой, когда:

```
✅ Все тесты проходят:
   pytest -q
   Результат: 100% pass, 0 failures

✅ Линтер чистый:
   ruff check .
   mypy execution/ model/ features/ data/
   Результат: 0 ошибок

✅ Покрытие тестов ≥ 70%:
   pytest --cov=. --cov-report=term-missing
   Результат: ≥ 70%

✅ Миграции применены:
   python -m scripts.migrate --dry-run
   Результат: "No pending migrations"

✅ Безопасность проверена:
   pip-audit -r requirements.txt
   python -m scripts.security_audit
   Результат: 0 критических уязвимостей

✅ Документация актуальна:
   python -m scripts.check_doc_links
   Результат: 0 сломанных ссылок

✅ Система запускается:
   DATA_MODE=paper python -m scripts.run_bot
   Результат: без ошибок, /api/health возвращает 200

✅ Все задачи ТЗ выполнены или задокументировано почему нет
```

### Что делать при конфликтах

```
1. Если изменение в ТЗ конфликтует с существующим кодом:
   → Сначала написать тест, который показывает текущее поведение
   → Затем изменить код
   → Тест должен показать новое поведение

2. Если задача не может быть выполнена без изменения архитектуры:
   → Задокументировать изменение в docs/ARCHITECTURE.md
   → Получить подтверждение (если возможно)
   → Внести изменение с тестами

3. Если задача требует внешних зависимостей:
   → Добавить в requirements.in
   → Перегенерировать requirements.txt через pip-compile
   → Задокументировать зачем нужна зависимость
```

### Эскалация

```
Если агент не может выполнить задачу:
1. Записать причину в TODO.md
2. Создать issue с описанием проблемы
3. Перейти к следующей задаче
4. НЕ ломать работающий код ради невыполнимой задачи

Если агент не уверен в решении:
1. Выбрать самый безопасный вариант
2. Задокументировать альтернативы
3. Пометить как "требует проверки"
```

### Оценка времени

Зависит от скорости модели и способа выполнения:

**Вариант 1: Один агент, последовательно**
```
Скорость: ~50-100 токенов/сек (если "flash")
Генерация: 1 000 000 токенов / 75 токенов/сек = ~3.7 часа
+ Время на чтение контекста: ~2-3 часа
+ Время на тестирование: ~2-3 часа
ИТОГО: ~8-12 часов
```

**Вариант 2: Несколько агентов параллельно**
```
4 агента × разные фазы
ИТОГО: ~3-4 часа (но больше общих токенов из-за дублирования контекста)
Общие токены: ~1 500 000 - 2 500 000
```

**Вариант 3: Один агент, но с разбивкой на сессии**
```
10-15 сессий по 60-90 минут
ИТОГО: ~15-20 часов общего времени
Общие токены: ~800 000 - 1 500 000
```

### Реалистичный сценарий

Если модель действительно быстрая ("flash") и ты дашь ей достаточно контекста:

```
Оптимистично: 4-6 часов, ~800K токенов
Реалистично: 8-12 часов, ~1M токенов
Пессимистично: 24+ часа, ~2M токенов
```

### Важные оговорки

1. **Ограничение контекста.** Если у модели контекст 128K или 256K токенов, она не сможет держать всё ТЗ + весь проект в памяти одновременно. Придётся разбивать на сессии.

2. **Качество > скорость.** Быстрая генерация кода не означает качественный код. После каждой фазы нужно запускать тесты.

3. **Итерации.** Первый проход никогда не идеален. Обычно нужно 2-3 итерации для каждой задачи.

4. **Тесты — самое важное.** Если агент напишет код без тестов, это не выполнено. Тесты занимают ~30-40% времени.

### Рекомендация

Если это действительно "flash" модель с большим контекстом:

```
1. Разбей ТЗ на 6-8 фаз (как в инструкциях выше)
2. Для каждой фазы дай агенту:
   - Соответствующую часть ТЗ
   - Релевантные файлы проекта
   - Инструкции из этого документа
3. После каждой фазы запусти тесты
4. Если тесты падают — дай агенту исправить
5. Только после зелёных тестов переходи к следующей фазе
```
